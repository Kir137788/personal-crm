# Design

## Context

См. `proposal.md` для мотивации. Сейчас контакты загружаются одним списком, фильтруются и разбиваются на страницы в клиентском компоненте. Данные контакта собираются серверными запросами к PostgreSQL; отдельной сущности групп и стандартного unit-тестового раннера в проекте пока нет. Новая модель должна быть добавочной: существующие контакты, заметки и напоминания не изменяются.

## Goals / Non-Goals

**Goals:**

- Хранить группы независимо от контактов и поддержать связь многие-ко-многим.
- Выполнять создание контакта с группами и замену состава групп атомарно.
- Возвращать контакты вместе с группами без отдельного запроса для каждой строки.
- Сохранить текущую клиентскую модель поиска и пагинации, добавив к ней один групповой фильтр.
- Ввести Vitest и реализовать каждый сценарий спецификации по циклу «красный тест → код → зелёный тест».
- Сохранить тёплый адаптивный интерфейс и существующие состояния ошибок.

**Non-Goals:**

- e2e-тесты, Playwright, GitHub Actions и защита ветки — следующие уроки.
- Вложенные группы, права доступа, общие группы между пользователями, автоматические правила распределения и массовое изменение контактов.
- Изменение существующей nginx-авторизации, напоминаний и журнала общения.
- Выкатка и заполнение производственной базы группами в рамках этого изменения.

## Decisions

### 1. Отдельные таблицы для групп и связей

Добавляем таблицу `contact_groups` с UUID, отображаемым названием, нормализованным названием и временными метками. Таблица `contact_group_memberships` содержит `contact_id` и `group_id`; составной первичный ключ исключает повтор одной связи. Оба внешних ключа удаляют строки связей каскадно, но удаление группы не затрагивает таблицу контактов.

Альтернатива — хранить массив названий в контакте. Она проще в начале, но затрудняет переименование, уникальность, удаление и целостность, поэтому не подходит.

### 2. Отдельное нормализованное название

Сервер удаляет пробелы по краям и строит `normalized_name` в нижнем регистре. Уникальный индекс базы остаётся последней защитой от одновременного создания дублей. Пользователь видит сохранённое отображаемое название, а конфликт получает статус 409 без внутренних подробностей.

Альтернатива — проверять повторы только запросом перед записью. При двух одновременных запросах такая проверка допускает дубль, поэтому одной её недостаточно.

### 3. Атомарные операции с составом групп

`POST /api/contacts` принимает необязательный список уникальных `groupIds`; контакт, первая заметка и связи сохраняются в одной транзакции. Для существующего контакта отдельная операция `PUT /api/contacts/:id/groups` принимает полный желаемый список и версию контакта. Сервер блокирует контакт, проверяет существование всех групп, заменяет связи и обновляет версию. При конфликте версии возвращается 409, при неизвестной группе — 400 или 404, без частичного изменения.

Альтернатива — отдельные запросы «добавить» и «убрать» для каждой метки. Они создают промежуточные состояния и усложняют повтор после сетевой ошибки.

### 4. API управления группами

Используются `GET/POST /api/groups` и `PATCH/DELETE /api/groups/:id`. Серверная валидация едина для создания и переименования. Удаление выполняется одним запросом после подтверждения в интерфейсе; каскад удаляет только строки связей. Ответы различают неверный ввод, конфликт названия, отсутствие записи и временную недоступность базы.

Альтернатива — проводить все действия через API контактов. Это смешивает жизненный цикл самостоятельной сущности группы с редактированием одного контакта.

### 5. Загрузка и фильтрация без N+1

Сервер возвращает каждый контакт с массивом его групп, используя агрегирующий запрос или два пакетных запроса. Список групп загружается отдельно один раз. Фильтр применяется на клиенте перед существующей пагинацией: сначала выбранная группа или «Без группы», затем текстовый поиск, затем сортировка и разбиение на страницы. При удалении выбранной группы фильтр переключается на «Все».

Альтернатива — серверная фильтрация. Сейчас приложение всё равно загружает весь список и считает общие показатели на клиенте; отдельная серверная пагинация стала бы более крупной несвязанной переделкой.

### 6. Интерфейс групп

Управление группами размещается рядом с фильтрами списка. Группы показываются компактными метками в строке и карточке. В форме нового контакта и в карточке используется общий элемент множественного выбора из уже созданных групп. Черновик выбора не меняет подтверждённые данные до успешного ответа сервера; при ошибке выбор остаётся доступным для повтора.

На узком экране фильтры и выбор переносятся на несколько строк без горизонтальной прокрутки всей страницы. Управление с клавиатуры и видимый фокус сохраняются.

### 7. Unit-тесты вокруг наблюдаемого поведения

Добавляем Vitest как dev-зависимость и команду `pnpm test`. Нормализация названия, проверка состава групп, фильтрация и переходы состояния интерфейса выделяются в чистые функции. Серверные операции отделяют правила от доступа к базе, чтобы зависимости можно было подменить в unit-тестах. Название каждого теста связывается со сценарием OpenSpec; перед реализацией сценария тест запускается и обязан упасть по ожидаемой причине.

Реальную связку браузера и PostgreSQL в этом изменении проверяем вручную. Автоматическая e2e-проверка на настоящей базе будет добавлена следующим этапом.

## Risks / Trade-offs

- **[Расхождение нормализации между приложением и базой]** → хранить рассчитанное сервером `normalized_name`, покрыть русские варианты регистра тестами и закрепить уникальность индексом.
- **[Частичное сохранение контакта и групп]** → проверять все идентификаторы до изменения и выполнять запись в одной транзакции.
- **[Устаревшая карточка перезапишет свежий состав групп]** → передавать `updatedAt`, блокировать контакт и возвращать 409 при конфликте.
- **[Много меток перегрузят строку таблицы]** → переносить метки внутри ячейки и проверять мобильную ширину вручную; искусственный лимит на количество групп не вводить.
- **[Клиентская фильтрация со временем станет медленной]** → оставить её в соответствии с текущей архитектурой; переход на серверную пагинацию рассматривать отдельно при подтверждённой проблеме производительности.
- **[Unit-тесты проверят внутренности вместо поведения]** → тестировать входы, результаты и ошибки доменных операций, не закрепляя структуру React-компонентов или SQL.

## Migration Plan

1. Добавить миграцию с двумя новыми таблицами и индексами. Существующие строки контактов не обновляются и автоматически считаются контактами без групп.
2. До изменения API прогнать миграцию на локальной базе и проверить сохранность количества и данных контактов.
3. Реализовать чтение групп, затем операции управления и назначения по TDD.
4. Подключить интерфейс и вручную проверить основной сценарий на локальной базе.
5. В этом уроке изменение только коммитится. Публикация, CI и производственная миграция выполняются после соответствующих этапов курса.

При ручном откате старый образ игнорирует новые таблицы, поэтому их можно временно оставить. Удалять таблицы и данные автоматически нельзя; отдельная обратная миграция допустима только после резервной копии и явного решения владельца.
