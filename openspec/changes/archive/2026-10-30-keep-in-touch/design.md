# Design

## Context

См. proposal.md о назначении изменения. В `lib/schema.ts` сейчас одна таблица contacts с notes и updatedAt. PATCH `/api/contacts/[id]` перезаписывает notes с проверкой updatedAt; GET `/api/contacts` возвращает все контакты, поиск и страницы по 50 строк выполняются в браузере. Карточка и список находятся в `components/contacts-app.tsx`. `scripts/migrate.ts` применяет журнал Drizzle до запуска новой версии. Даты последнего общения в модели нет.

## Goals / Non-Goals

**Goals:** отделить дату разговора от редактирования, сохранить старый текст, сделать расчёт проверяемым с фиксированными часами, сохранить защиту от конкурирующих правок.

**Non-Goals:** новые сервисы, очереди, фоновые задания на сервере, замена авторизации или самостоятельная выкатка при подготовке документов.

## Decisions

### Модель данных и достоверность даты

Добавить contacts.contactIntervalDays (nullable integer с CHECK для 7/30/90/365) и reminderEnabledAt (timestamptz). NULL интервала означает отключение; переход из NULL в активное значение фиксирует серверное время, изменение активного интервала сохраняет его. Отключение очищает reminderEnabledAt. Последнюю известную дату получать как MAX(occurredAt) истории, а не дублировать в контакте.

Создать contact_notes: id UUID, contactId FK с ON DELETE CASCADE, body, occurredAt nullable, createdAt, updatedAt и признак legacy. Индекс по contactId и occurredAt; уникальная legacy-запись на контакт. Для новых записей occurredAt задаёт сервер и не изменяет при исправлении. Для перенесённой заметки occurredAt=NULL; createdAt означает перенос, не общение. Сохранить contacts.notes на переходный период. Альтернатива «использовать contacts.updatedAt» отвергнута: это недостоверная дата общения.

### Переход со старой версии

Аддитивная миграция создаёт историю и переносит непустой contacts.notes без изменения текста. Чтобы не потерять запись старой версии между миграцией и заменой контейнера, добавить триггер синхронизации старого notes в единственную legacy-запись (INSERT/UPDATE, только при изменении notes). Он никогда не задаёт occurredAt и не трогает новые записи. Пустой старый текст не создаёт новую legacy-запись; очистка уже существующего текста старым клиентом не удаляет сохранённую историю. Исправление legacy-записи новым API синхронизирует старое поле в той же транзакции. Это дороже одноразового backfill, но закрывает окно записи при выкатке и ручном откате.

### API и конкурентность

- GET `/api/contacts`: сохранить форму массива и существующие поля для перехода, добавить интервал, точку включения, lastContactAt, hasNotes. Счётчик «С заметками» и маркер строки используют историю, не старое поле.
- GET `/api/contacts/[id]/notes`: история выбранного контакта, без загрузки всех текстов для общего списка.
- POST на тот же адрес: body и UUID операции, используемый как id записи. Повтор с тем же id, контактом и текстом возвращает исходную запись, с отличающимся содержимым — 409. Это защищает от повторной отправки после потери ответа; UI удерживает UUID до подтверждения.
- PATCH `/api/contacts/[id]/notes/[noteId]`: body и ожидаемый updatedAt. Условное обновление, 409 при конфликте; occurredAt неизменен. Запись проверяется на принадлежность контакту.
- PATCH `/api/contacts/[id]/reminder`: допустимый интервал/null и ожидаемый updatedAt контакта; блокировка строки в транзакции и 409 при конфликте.
- Существующий PATCH с notes обслуживает только legacy-запись, не означает новый разговор. Новый интерфейс им не пользуется.
- POST контакта: создание контакта и первой новой заметки атомарно, если текст введён; контакту по умолчанию не напоминать. Не создавать вторую legacy-копию новой заметки.
- Невалидное тело — 400, отсутствующий контакт/чужая запись — 404, конфликт — 409, недоступность базы — 503. Ответы не содержат секретов; проверка UUID и Zod до запросов. Непустой текст не длиннее 20000 символов, пробельность проверять без изменения сохранённого текста.

### Расчёт и список

Чистая функция принимает интервал, lastContactAt, reminderEnabledAt и now: base=lastContactAt ?? reminderEnabledAt; due=base+interval*86400000. Просрочка только now>due, N=ceil((now-due)/86400000). Серверный GET `/api/contacts/due` возвращает serverNow и весь отсортированный список с dueAt и overdueDays, Cache-Control:no-store. Вторичная сортировка по русскому имени, затем id. Нагрузка текущего прототипа позволяет обойтись без пагинации этого блока; общий список сохраняет свою пагинацию и поиск. Расчёт не зависит от часового пояса браузера. Альтернатива календарных месяцев отклонена по решению пользователя.

После мутаций перезапрашивать затронутую историю, общий список и блок просрочки; также при возврате фокуса и каждые 60 секунд видимой страницы. Не перекрывать более свежие данные запоздавшими ответами. Не сбрасывать несохранённые черновики при обновлении.

### Интерфейс

В существующем Sheet добавить подписанный select частоты с отдельным сохранением, редактор новой заметки и историю с действием исправления. Сохранить защиту закрытия с черновиком, блокировку повторного клика и понятную ошибку. Над contacts-panel разместить блок просрочки с отдельными загрузкой, ошибкой и пустым состоянием. Использовать существующие CSS-токены, Button и Input, доступные подписи и видимый фокус. Историю показывать новые записи сначала, неизвестную дату в конце.

### Уточнения для приёмки

Технические договорённости проекта спецификации: ровно в срок просрочки ещё нет; неполный день просрочки округляется вверх; блок не зависит от поиска общего списка; повторное включение без известного общения начинает новый отсчёт. Они явно описаны в сценариях для проверки перед реализацией.

## Risks / Trade-offs

- Старый клиент/образ не умеет показывать новую историю → поле и триггер совместимости сохраняются; новые записи остаются в базе, но в старом интерфейсе недоступны. Полная функциональная совместимость отката не обещается.
- Конкурирующие исправления → проверка версии, сохранение черновика и явный конфликт.
- Потеря ответа POST → ключ операции и повтор без дублирования и переноса даты.
- Большое количество просроченных → для текущего объёма список целиком; при росте отдельное изменение пагинации.
- Удаление контакта находится в другой ветке → после объединения проверить FK cascade и согласовать изменения Sheet, не заменяя уже добавленный сценарий удаления.

## Migration Plan

1. На изолированной тестовой базе применить миграцию к старой схеме с пустой, непустой и многострочной заметкой; проверить точность переноса и повторный запуск.
2. Проверить запись старым API после миграции, создание новым API без дублей, исправление legacy и каскадное удаление тестового контакта.
3. Перед будущей выкаткой сделать резервную копию базы без вывода содержимого. Через PR включить миграцию в журнал Drizzle; существующий CI применит её перед сменой приложения.
4. Проверить /health, создание заметки, срок и сохранность истории. Производственные данные ради теста не менять без отдельного согласования.
5. При сбое остановить выкатку и сообщить пользователю. Откат образа — только по его решению; таблицы, новые записи и старое поле не удалять, обратную разрушительную миграцию не запускать. После возврата новой версии история снова доступна.
