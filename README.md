# Круг — личная CRM

Люди, откуда вы знакомы, контакты и заметки после разговоров. Без регистрации, уведомлений и офлайн-режима.

## Запуск

Требуются Node.js 24 LTS, pnpm и запущенный Docker Desktop.

```bash
cd "/Users/kirprovans/Desktop/Курс/module-1/personal-crm"
docker compose up -d --wait
pnpm install
pnpm db:migrate
pnpm db:seed
pnpm build
pnpm start
```

Откройте http://127.0.0.1:3000. Для разработки вместо двух последних команд используйте `pnpm dev`. Приложение работает на Mac, в Docker — только PostgreSQL 18.

Настройки подключения уже находятся в `.env`. Не публикуйте этот файл. На новой машине заполните переменные, перечисленные в `.env.example`: POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_PORT и DATABASE_URL. Значения в пример не включены. Порт по умолчанию — 5432, адрес базы — 127.0.0.1. DATABASE_URL должен соответствовать остальным параметрам. Пароль не выводится приложением или скриптами.

## Проверка главного сценария

1. Откройте приложение: все контакты доступны в списке по 50 на страницу.
2. Нажмите «Добавить контакт». Имя обязательно; остальные поля необязательны.
3. Закройте карточку и найдите контакт через поле поиска (или ⌘ K).
4. Откройте карточку, введите текст в «Новая заметка», нажмите «Добавить заметку».
5. Перезагрузите страницу или откройте тот же адрес в другом браузере: контакт и заметка сохранятся.

Поиск не зависит от регистра и работает по всему списку, включая имя, почту, телефон и контекст знакомства. Контакты сортируются по имени. При закрытии карточки с несохранённым текстом приложение просит подтверждение. История хранит отдельные записи; если запись уже изменена в другом окне, приложение не перезаписывает её молча.

## Данные и архитектура

- Next.js App Router, React, TypeScript, Tailwind CSS, локальные компоненты shadcn/ui.
- Браузер обращается только к Next.js API. Доступ к PostgreSQL через Drizzle выполняется на сервере.
- `lib/schema.ts` — схема; `drizzle/` — SQL-миграции и журнал миграций.
- `pnpm db:generate` — создать миграцию после изменения схемы.
- `pnpm db:migrate` — применить миграции.
- `pnpm db:seed` — добавить 1000 вымышленных контактов. Повторный запуск не создаёт дубликаты и не перезаписывает имеющиеся записи.
- Тестовые адреса используют домен example.com; реальные телефонные номера не генерируются.
- После проверки интерфейса дополнительно сохранён один учебный контакт «Вера Тестовая» с заметкой, всего 1001 запись.
- `pnpm typecheck` и `pnpm build` — проверка типов и production-сборки.
- `pnpm-lock.yaml` фиксирует версии зависимостей.

Данные сохраняются в именованном Docker volume `personal-crm_postgres_data`. `docker compose down` останавливает базу с сохранением данных. Не используйте `down -v`, если данные нужно сохранить.

## Работа в Codex

Откройте эту папку как основной локальный проект. `AGENTS.md` подключает инструкции `CLAUDE.md` и запрещает чтение `.env*`. В `.codex/config.toml` задан профиль запрета чтения. Конфигурация загружается в новом сеансе доверенного проекта; управляемые настройки приложения могут иметь приоритет. Скрипты приложения и Compose используют переменные внутри процесса, без вывода секретов.


## OpenSpec: работа над фичами

Установлен OpenSpec 1.15.0 по официальной инструкции через Homebrew (`brew install openspec`).
Интеграция с Codex находится в `.agents/skills/openspec-*`, настройки — в `openspec/config.yaml`.
На новой машине после установки CLI интеграцию можно восстановить командой:

```bash
openspec init --tools codex --language Russian --profile core --no-animation
```

Описания, требования, дизайн и задачи пишем на русском. Обязательные заголовки формата
OpenSpec, ключевые слова SHALL/MUST, имена файлов и идентификаторы остаются на английском.

Откройте новый сеанс Codex в папке этого проекта, чтобы он обнаружил установленные навыки.
Команды ниже отправляются в чат Codex, а не в Терминал:

- `$openspec-explore` — обсудить идею и ограничения.
- `$openspec-propose keep-in-touch` — подготовить предложение, требования, дизайн и задачи; сначала уточнить неясные требования.
- `$openspec-update-change` — скорректировать подготовленные материалы.
- `$openspec-apply-change keep-in-touch` — реализовать согласованные задачи.
- `$openspec-sync-specs` — перенести согласованные изменения в основные спецификации.
- `$openspec-archive-change keep-in-touch` — архивировать завершённую фичу.

В курсе используются команды Claude `/opsx:*`; здесь используем навыки Codex `$openspec-*`.
Рабочие материалы хранятся в `openspec/changes/`, основные требования — в `openspec/specs/`.
Проверка подключения в Терминале: `openspec --version` и `openspec list`.
Подготовка требований не запускает реализацию: к коду переходим после их согласования.

## Автовыкатка на сервер

Push в `main` запускает `.github/workflows/deploy.yml`: GitHub собирает Docker-образ,
публикует его в GHCR с тегом SHA коммита и вызывает `deploy/ci.sh`.
Сервер скачивает образ, запускает миграции отдельным контейнером из этого же образа,
затем обновляет приложение. Ошибка миграции останавливает выкатку до замены приложения.
Проверки `/health` внутри сервера и через HTTPS должны вернуть 200 и SHA нового коммита.
При ошибке проверки workflow становится красным; автоматического отката нет.

Приложение: https://app.provansov.ru (вход через nginx по логину и паролю).
Проверка доступности: https://app.provansov.ru/health (без авторизации, только статус и версия).
Лендинг https://provansov.ru обслуживается отдельно и не обновляется этим workflow.

### Новая версия

1. Внесите изменения. Если меняется схема базы, создайте и включите SQL-миграцию в коммит.
2. Проверьте `pnpm typecheck` и `pnpm build`.
3. Создайте коммит в рабочей ветке, отправьте её на GitHub и откройте PR в `main`. После проверки слейте PR.
4. Дождитесь зелёного запуска Deploy CRM во вкладке Actions на GitHub.
5. Откройте приложение и проверьте нужный сценарий.

Тестовые данные не добавляются при каждом push. Разовая команда
`ssh crm 'sudo /usr/local/sbin/crm-release seed'` создаёт 1000 вымышленных контактов
и записывает маркер; повторное выполнение ничего не добавляет.

### Устройство сервера

- Docker Compose `-p prod`; настройки: `/opt/personal-crm/compose.yaml`.
- Секреты: `/opt/personal-crm/.env`, владелец root, права 600. Агент файл не читает и не записывает.
- Переменные: `POSTGRES_USER`, `POSTGRES_DB`, `POSTGRES_PASSWORD`, `DATABASE_URL`.
  База и пользователь — `krug`, внутренний адрес базы — `db:5432`.
- Используется существующий том `krug_postgres_data`. При первом переходе старая пара
  контейнеров останавливается; перед этим создаётся `/opt/personal-crm/before-adoption.dump`.
  Возможен короткий перерыв. Старые контейнеры и исходные настройки сохранены.
- База не публикует порт; приложение слушает только `127.0.0.1:3000`.
- nginx принимает внешний HTTPS. Логи Docker ограничены 3 файлами по 10 МБ на контейнер.
- После успешной выкатки сохраняются текущий и предыдущий SHA-образ этого приложения.
  Старый образ прототипа не удаляется автоматически.
- Ключ CI в GitHub Secrets `DEPLOY_SSH_KEY`; доверенный ключ сервера — `DEPLOY_KNOWN_HOSTS`.
  SSH-ключ CI ограничен forced command: обычный shell, SCP, проброс портов запрещены.
- Сценарии находятся в `deploy/`. Workflow передаёт `remote.sh` серверу;
  сервер принимает только версию, предварительно установленную администратором.
- Root-помощник `/usr/local/sbin/crm-release` принимает только выкатку SHA,
  проверку статуса, разовое заполнение базы и ручной откат. Полного sudo без пароля нет.
- GHCR авторизуется временным токеном запуска Actions; настройки авторизации удаляются после скачивания.

Для первичной установки администратор запускает `sudo bash deploy/install.sh` на сервере,
затем сам подготавливает `.env`. Обновление привилегированного помощника, Compose или
утверждённого `remote.sh` также требует ручной установки через sudo. Обычные изменения
приложения выкатываются автоматически.

### Проверка и ручной откат

```bash
ssh crm 'sudo /usr/local/sbin/crm-release status'
curl --fail https://app.provansov.ru/health
# Только по решению человека; доступен после двух успешных версий:
ssh crm 'sudo /usr/local/sbin/crm-release rollback'
```

Откат переключает образ приложения на предыдущую успешную версию, но не отменяет
миграции базы. Поэтому изменения схемы должны сохранять совместимость с предыдущей
версией приложения. Не применяйте `docker compose down -v`: это удаляет данные.

## Не терять связь (keep-in-touch)

В карточке выберите частоту и нажмите «Сохранить частоту». По умолчанию стоит
«Не напоминать». Неделя, месяц, квартал и год равны 7, 30, 90 и 365 суткам по
24 часа. Срок начинается с последней новой заметки, а если её дата неизвестна —
с включения напоминания. Смена активной частоты не сбрасывает точку отсчёта.
Отключение убирает контакт из блока. Повторное включение без известного общения
начинает новый отсчёт.

Блок «Пора связаться» находится над общим списком и не зависит от его поиска и
страницы. Самые просроченные контакты сверху. Ровно в момент срока контакт ещё
не просрочен, после него неполный день округляется вверх. Обновление происходит
после сохранения, при возврате к странице и каждую минуту, пока она видима.
Например, общение 20 октября в 12:00 UTC с интервалом 7 дней даёт срок 27 октября
в 12:00 UTC; 30 октября в 12:00 UTC просрочка составляет 3 дня.

Новая заметка добавляется в историю и отмечает общение. «Исправить» меняет текст,
но не дату разговора. Старый текст переносится целиком одной записью «Дата общения
неизвестна». Для счётчика заметок учитывается вся история. При сбое сети черновик
сохраняется; повтор добавления использует тот же идентификатор операции, без дубля.
При конфликте исправления обновите историю, сравните тексты, затем откройте редактор
заново. Не закрывайте карточку, пока нужный черновик не скопирован или не сохранён.

### API и миграция

- `GET /api/contacts/[id]/notes` — история выбранного контакта.
- `POST /api/contacts/[id]/notes` — `{id, body}`, UUID операции сохраняется для повтора.
- `PATCH /api/contacts/[id]/notes/[noteId]` — `{body, updatedAt}`, версия записи обязательна.
- `PATCH /api/contacts/[id]/reminder` — `{contactIntervalDays, updatedAt}`, интервал 7/30/90/365 или null.
- `GET /api/contacts/due` — `{serverNow, contacts}`, каждый контакт содержит dueAt и overdueDays.
- Список контактов дополнен lastContactAt, hasNotes, contactIntervalDays и reminderEnabledAt.

Миграция `0001_friendly_rogue.sql` аддитивная: создаёт историю и переносит текст.
Старое поле сохранено; триггер переносит записи старого клиента в legacy-запись
и не меняет даты новых разговоров. При ручном откате старый образ не показывает
новую историю, но она остаётся в базе. Обратную миграцию с удалением таблицы не
применять. Перед будущей выкаткой нужна резервная копия; сама выкатка — через PR.

### Проверка разработки

Тесты используют исключительно отдельный временный контейнер и базу `crm_test`:

```bash
docker run -d --name crm-keep-in-touch-test -e POSTGRES_HOST_AUTH_METHOD=trust -e POSTGRES_DB=crm_test -p 127.0.0.1:15439:5432 postgres:18
node --conditions=react-server --import tsx scripts/test-keep-in-touch.mts
pnpm typecheck
pnpm build
```

Дождитесь готовности тестовой базы перед тестом. Скрипт пересоздаёт только её схему,
не загружает `.env` и не принимает адрес рабочей базы. Тестовый порт доступен только
с этого Mac. После тестов остановите временный контейнер:
`docker stop crm-keep-in-touch-test`.

Для ручной проверки: открыть контакт → сохранить неделю → добавить заметку →
увидеть запись и следующий срок → исправить текст → убедиться, что срок не изменился →
перезагрузить страницу. Проверьте также отмену закрытия с черновиком, отключение
напоминания и карточку на мобильной ширине. Данные для искусственной просрочки
создавайте только в тестовой базе.

Проверка 30 октября 2026: миграции, API, сборка и браузер проверены на установленном Node.js 26.13.0. Локальный Node.js 24.22.0 аварийно завершал генератор Drizzle; системную версию и зависимости проекта в этой доработке не меняли. Для воспроизведения проверок на этом Mac можно предварить команду `PATH="/opt/homebrew/opt/node/bin:$PATH"`.


## Удаление контакта

Откройте карточку, нажмите «Удалить контакт» и проверьте имя в подтверждении.
«Отмена» сохраняет контакт и несохранённый текст заметки. «Да, удалить» навсегда
удаляет контакт со всеми заметками; восстановления нет. Список, счётчики и страницы
обновляются автоматически. При ошибке карточка остаётся открытой для повторной попытки.

Требования: `openspec/specs/delete-contact/spec.md`.
При запущенной локальной CRM тест API выполняется командой
`node scripts/test-delete-contact.mjs`: он создаёт только собственные тестовые записи
и удаляет их после проверки. На сервере этот тест не запускается.

Перед выкаткой изменения схемы загрузите `deploy/backup.sh` на сервер и запустите
через sudo. Скрипт сохраняет закрытую резервную копию PostgreSQL в
`/var/backups/personal-crm/` и проверяет её оглавление, не выводя данные.
